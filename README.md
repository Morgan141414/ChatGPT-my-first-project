Техническое задание (ТЗ)
Разработка собственного AI-ассистента — аналог ChatGPT
Fullstack project
Учебный командный проект
AI / LLM

Рабочее название: NOVA AI

Технологический стек:
- Backend: Python + FastAPI.
- Frontend: React + TypeScript.
- AI: бесплатный API языковой модели (LLM).
- Database: PostgreSQL.
- ORM: SQLAlchemy.
- Authentication: JWT.
- Styling: Tailwind CSS.
- Deployment: Docker.
Главная цель: разработать собственный веб-сервис искусственного интеллекта, внешне и функционально напоминающий ChatGPT. Пользователь должен иметь возможность регистрироваться, создавать новые диалоги, отправлять сообщения, получать ответы ИИ, просматривать историю переписки и управлять своими чатами.

Важно: команда не должна обучать собственную большую языковую модель с нуля. На первом этапе мы создаём собственную AI-платформу, которая использует готовую модель через API. Именно интерфейс, backend, архитектура, управление диалогами и пользовательский опыт будут нашей собственной разработкой.

FRONTEND TEAM

4.6. Интеграция искусственного интеллекта
Это центральная часть проекта.

Необходимо реализовать отдельный AI Service, который отвечает за взаимодействие с языковыми моделями.

Рекомендуемый первый провайдер — Google Gemini API.

Также можно подключить OpenRouter, предоставляющий доступ к различным бесплатным моделям.

На 5 ноября 2026 года:
- Gemini предлагает бесплатный уровень API для определённых моделей с ограничениями по квотам.
- OpenRouter предлагает бесплатные варианты моделей с ограничениями по количеству запросов.
- Бесплатный доступ не означает отсутствие лимитов, гарантированной доступности или права на неограниченное коммерческое использование.
Источники:
- Gemini API — официальные тарифы.
- OpenRouter — бесплатные модели.
- Сравнение доступных API-провайдеров.
Требование к архитектуре: AI Service должен позволять менять провайдера без переписывания всей серверной логики.

Например:

Далее каждый провайдер реализует собственный класс:
BaseAIProvider

      |------------------|
      |                  |

Это позволит в будущем подключать новые модели без изменения логики чатов, авторизации и базы данных.
4.7. Система контекста диалога
ИИ должен учитывать предыдущие сообщения.

Пример:

Пользователь: «Меня зовут Алекс».

ИИ: «Приятно познакомиться, Алекс!»

Пользователь: «Как меня зовут?»

ИИ: «Тебя зовут Алекс».

Для этого Backend должен передавать модели не только последнее сообщение, но и предыдущую историю диалога.

Пример структуры запроса:
{
  "model": "selected-model",
  "messages": [
    {
      "role": "system",
      "content": "Ты полезный AI-ассистент."
    },
    {
      "role": "user",
      "content": "Меня зовут Алекс."
    },
    {
      "role": "assistant",
      "content": "Приятно познакомиться!"
    },
    {
      "role": "user",
      "content": "Как меня зовут?"
    }
  ]
}


Необходимо предусмотреть ограничение контекста, чтобы не отправлять всю переписку бесконечно.

В первой версии достаточно:
- Последних N сообщений.
- Ограничения по количеству токенов.
- Возможности в дальнейшем добавить автоматическое суммирование старых сообщений.
4.8. Streaming — потоковая генерация
Обязательная функция MVP
Вместо ожидания полного ответа модель должна передавать результат частями.

Принцип работы:
Пользователь отправляет сообщение

React → FastAPI

FastAPI → AI Provider

AI генерирует ответ частями

FastAPI передаёт chunks через SSE

React постепенно отображает ответ

Полный ответ сохраняется в PostgreSQL


Рекомендую использовать Server-Sent Events (SSE) для первой версии.

Backend должен отправлять события:
event: start
data: {"message_id":"123"}

event: token
data: {"content":"Привет"}

event: token
data: {"content":"! Чем"}

event: token
data: {"content":" могу помочь?"}

event: done
data: {"finish_reason":"stop"}


Также предусмотреть событие error.

Важно: необходимо корректно обрабатывать отключение пользователя, остановку генерации, тайм-ауты и ошибки провайдера. Если генерация прерывается, нельзя сохранять незавершённый ответ как полноценный.

4.10. Безопасность Backend
Обязательные требования:
1. Хеширование паролей через Argon2.
2. API-ключи только в переменных окружения.
3. Проверка JWT.
4. Проверка владельца каждого чата.
5. Ограничение размера сообщений.
6. Rate limiting.
7. Валидация входящих данных.
8. Защита от SQL Injection.
9. Защита от XSS на уровне безопасного отображения контента.
10. Ограничение CORS доверенными доменами.
11. Защита от перебора паролей.
12. Запрет на запись секретов в логи.
13. Обработка ошибок внешнего AI API.
14. Тайм-ауты и ограничение одновременных запросов.
Отдельно: system prompt не является полноценной защитой от prompt injection. Модель не должна иметь прямого доступа к секретам, базе данных или административным функциям.

5. Контракт взаимодействия Frontend и Backend
Критически важный раздел
Обе команды должны работать по одному API-контракту. Нельзя допускать ситуации, когда Frontend ожидает один формат данных, а Backend возвращает другой.

Все API-маршруты должны иметь префикс:

/api/v1/
5.1. Основные API endpoints
Method	Endpoint	Назначение
POST	/auth/register	Регистрация
POST	/auth/login	Вход
POST	/auth/refresh	Обновление токена
POST	/auth/logout	Выход
GET	/users/me	Профиль пользователя
POST	/chats	Новый диалог
GET	/chats	Список диалогов
GET	/chats/{id}	Информация о диалоге
PATCH	/chats/{id}	Переименование
DELETE	/chats/{id}	Удаление
GET	/chats/{id}/messages	История сообщений
POST	/chats/{id}/messages/stream	Отправка сообщения и генерация ответа
GET	/models	Доступные модели

5.2. Пример создания чата
Request:
POST /api/v1/chats
Authorization: Bearer <access_token>
Content-Type: application/json


Body:
{
  "title": "Новый диалог",
  "model": "default"
}


Response:
{
  "id": "uuid",
  "title": "Новый диалог",
  "model": "default",
  "created_at": "2026-11-05T12:00:00Z"
}


5.3. Пример отправки сообщения
Request:
POST /api/v1/chats/{chat_id}/messages/stream


Body:
{
  "content": "Объясни, что такое Python",
  "model": "default"
}


Ответ передаётся через SSE, а не обычный JSON.

Frontend должен уметь:
- Открывать поток.
- Читать события.
- Обновлять сообщение по мере получения данных.
- Обрабатывать завершение.
- Обрабатывать ошибки.
- Закрывать соединение при отмене генерации.
Для этого можно использовать fetch() и ReadableStream. Обычный EventSource не подходит для данного POST-запроса, поскольку не поддерживает отправку JSON-body и произвольных заголовков авторизации.
5.4. Стандарт ошибок API
Все ошибки должны возвращаться в едином формате:
{
  "error": {
    "code": "AI_PROVIDER_ERROR",
    "message": "Не удалось получить ответ от AI",
    "details": null
  }
}


Основные коды:
HTTP	Code	Значение
400	VALIDATION_ERROR	Неверные данные
401	UNAUTHORIZED	Нет авторизации
403	FORBIDDEN	Нет доступа
404	NOT_FOUND	Объект не найден
409	CONFLICT	Конфликт данных
413	PAYLOAD_TOO_LARGE	Слишком большой запрос
429	RATE_LIMITED	Превышен лимит
502	AI_PROVIDER_ERROR	Ошибка AI-провайдера
503	SERVICE_UNAVAILABLE	Сервис недоступен
504	AI_TIMEOUT	Истекло время ожидания


6. Дополнительные функциональные требования
Эти функции не должны мешать созданию первой версии, но архитектура должна позволять добавлять их в будущем.
6.1. Выбор AI-модели
Пользователь может выбирать модель из списка доступных.

Например:
- NOVA Default.
- Gemini Flash.
- Другие подключённые модели.
Необходимо предусмотреть возможность менять модель в рамках диалога, если провайдер это поддерживает.
6.2. Системные инструкции
Пользователь должен иметь возможность настраивать характер ИИ.

Примеры:
- Стандартный помощник.
- Преподаватель.
- Программист.
- Научный ассистент.
- Креативный помощник.
Для этого Backend должен поддерживать системные инструкции (system prompts).

Пример:
Ты — NOVA AI, интеллектуальный помощник.

Твои задачи:
1. Отвечать понятно и структурированно.
2. Не выдумывать факты.
3. Признавать, когда не знаешь ответа.
4. Использовать язык пользователя.
5. Предоставлять примеры, когда это необходимо.


6.3. Автоматическое название диалога
После первого сообщения система должна автоматически создавать короткое название чата.

Например:

Сообщение пользователя:

«Объясни, как работает машинное обучение».

Название:

«Основы машинного обучения».

Это можно сделать отдельным запросом к AI API либо простым алгоритмом на первом этапе.
6.4. Возможность остановки генерации
Во время генерации пользователь должен иметь возможность нажать Stop.

Требования:
- Frontend прекращает чтение потока.
- Backend пытается отменить текущий запрос к провайдеру.
- Соединение закрывается.
- Уже полученный текст сохраняется со статусом interrupted.
- Пользователь может отправить следующее сообщение.
6.5. Лимиты бесплатного использования
Поскольку мы используем бесплатный AI API, необходимо разработать систему ограничений.

Например, на первом этапе:
- Ограничение частоты отправки сообщений.
- Ограничение длины одного сообщения.
- Ограничение количества одновременных генераций.
- Ограничение длины контекста.
- Отображение пользователю сообщения при достижении лимита.
Конкретные квоты должны определяться тарифами выбранного провайдера, а не зашиваться в код как постоянные значения.

- Корректная работа нескольких пользователей одновременно.

10.3. Общая приёмка
Проект принимается, когда можно продемонстрировать следующий сценарий без ручного вмешательства разработчиков:
1. Новый пользователь регистрируется.
2. Авторизуется.
3. Создаёт диалог.
4. Отправляет сообщение.
5. Получает реальный ответ от AI API.
6. Видит постепенную генерацию ответа.
7. Отправляет уточняющий вопрос.
8. ИИ учитывает предыдущую переписку.
9. Перезагружает страницу.
10. Возвращается в диалог и видит историю.
Если все десять шагов работают, у нас есть полноценный MVP.

15. Мои организационные рекомендации
Я бы установил для проекта следующие правила:
1. Не писать весь проект в одном файле. Каждый компонент и модуль должны отвечать за конкретную задачу.
2. Не смешивать Frontend и Backend. Команды работают независимо, взаимодействуя через согласованный API.
3. Не использовать mock AI в финальной версии. Демонстрационные ответы допустимы только при разработке интерфейса. Финальная версия должна обращаться к настоящей языковой модели.
4. Не хранить историю только в браузере. История должна сохраняться в PostgreSQL.
5. Не допускать прямого доступа Frontend к AI API.
6. Проводить ежедневные короткие встречи. Каждый участник рассказывает, что сделал, что делает и что ему мешает.
7. Не принимать незавершённые задачи. У каждой задачи есть критерии готовности.
